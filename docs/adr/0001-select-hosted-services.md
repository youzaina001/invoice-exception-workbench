# Select hosted services for Invoice Triage

Status: accepted 2026-10-03. The workbench code for the hosted demonstration is in this branch. No deployment is claimed. The default local runtime remains the localhost workflow in `README.md`. Provider limits below are the decision's historical assumptions, not a current availability guarantee; recheck them before provisioning.

Adopt Neon for hosted PostgreSQL and Clerk for authentication in the first hosted release. R2 for file storage and Resend for application email wait for a later release that needs them. Publish a public landing page and documentation through Cloudflare Pages, automatically updated when commits reach the existing `master` branch. Keeping the current default branch avoids a branch migration. The sequence introduces shared persistence and sign-in before file storage and email workflows.

The first hosted release demonstrates the invoice workflow using synthetic examples behind invitation-only Clerk access, alongside the public landing page and documentation. Only invited reviewers may enter the operator application; public sign-up is outside this release. This keeps the initial audience controlled while the landing page and documentation remain publicly accessible. Accepting visitors' real invoices is outside this release; doing so would require a separate customer-isolation and operational design.

The Maintainer creates each invitation by hand in the Clerk dashboard. Clerk sends the invitation email. The application does not send mail and does not offer an invite screen. The Reviewer's first sign-in creates their Demo Workspace and its first Demo Attempt. Resend is not used for invitations.

This release does not use Cloudflare R2 or Resend. An uploaded CSV is parsed into rows in Neon and the original file is not kept. Application email waits for a later release that has a message of its own to send. R2 waits for a later release that keeps original invoice files.

Each invited reviewer receives a separate Demo Workspace and workflow progress. Reviewers cannot read or change one another's submissions, cases, check results, or audit evidence. This adds isolation work compared with one shared demo, but lets reviewers complete the workflow independently without coordinating visits.

Those workspaces share one Neon database. Postgres row-level security ties each submission, case, check result, and audit row to the signed-in reviewer, and the application connects as a role that cannot bypass those policies. A query that omits the reviewer still cannot cross into another Demo Workspace. A separate Neon project per reviewer was rejected because it splits provisioning across projects. Application-only filters were rejected because a missed filter can leak a workspace.

The Maintainer, who owns the Neon project, can inspect every Demo Workspace, including read-only past attempts. That access is for provisioning and for repairing a stuck walkthrough. The invoices are synthetic. The application role used by Reviewers cannot bypass row-level security, so this does not let one Reviewer read another.

Reviewers resume their saved progress when they return. A new Demo Attempt starts with no invoices. The public docs publish the sample CSVs, and the Reviewer uploads them, matching the local journey. A deliberate “Start fresh” action creates a new empty Demo Attempt and preserves the previous attempt, including its audit evidence, as read-only history in the same private Demo Workspace. Signing out or revisiting the application does not reset their work. Each Demo Workspace keeps at most five Demo Attempts: the current one and four read-only ones. Starting a sixth deletes the oldest attempt in that workspace. The cap stops one Reviewer from filling the shared 1 GB Neon allowance by repeating the walkthrough. The sample invoices are about 100 bytes each, so five attempts per Reviewer stay far below that allowance in ordinary use.

The hosted demo has a strict recurring budget of €0 and must use free offerings. A paid upgrade or usage overage is outside the agreed scope. Provider selection must account for free-plan limits and how usage stops before a charge; a free allowance on a metered service is not by itself a spending cap. Time-limited credits are not a sustainable hosting plan.

The existing FastAPI operator application runs on one Render Free web service. After 15 minutes without inbound traffic that service spins down, and the next visit takes about a minute while Render shows a loading page. The Cloudflare Pages site stays available during that wait. The instance disk is ephemeral, so submissions, cases, check results, and audit evidence stay in Neon. A keep-alive ping or cron is out of scope: Render cron jobs have a $1 monthly minimum, and intentionally keeping a free web service awake goes against Render's stated intent for the free tier. One always-awake service would also consume essentially all 750 free instance hours in the workspace, since a 31-day month has 744. Exhausting those hours suspends every free web service in the workspace until the next month. The Render workspace has no payment method, so a bandwidth or build-minute overage stops the free service instead of charging.

Neon for this demo is the free plan. Compute scales to zero after 5 minutes of inactivity, which cannot be disabled on that plan, and wakes in a few hundred milliseconds. The project includes 1 GB of storage and 100 CU-hours per month. Crossing the compute or transfer allowance suspends compute until the next period. Crossing 1 GB stops writes that would grow storage. Neither case bills an overage. Clerk stays on its free plan, and invitation-only access uses Clerk's invite-only mode. Clerk's paid allowlist is outside this release.

The decisions above were agreed on 2026-10-03. This decision does not claim a deployment exists.
